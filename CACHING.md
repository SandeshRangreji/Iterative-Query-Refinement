# Caching Methodology

This pipeline is expensive to run cold (indexing + sampling + topic modeling can take 20-30 min per query — see USAGE.md's Expected Runtime table), so every stage caches its output. This doc is the single source of truth for what's cached, where, keyed on what, and — critically — **what does NOT auto-invalidate when you change a config value**, which is the most common source of silently-stale results in this project.

See [PIPELINE.md](PIPELINE.md) for how these tiers map onto pipeline stages.

---

## The six cache tiers

### 1. Search indices — shared across all queries and topic models

- **BM25**: `cache/indices/bm25/{dataset}_b{b_param}_k1-{k1_param}_eps{epsilon}_stem-{stemmer}.pkl`
- **SBERT embeddings**: `cache/indices/embeddings/{model_name_with_slashes_and_dashes_underscored}/{dataset}_batch{batch_size}.pt`

Built by `src/search.py`'s `IndexManager`. The cache key is baked into the filename (dataset + BM25 hyperparameters, or dataset + embedding model + batch size), so *different parameter values produce different cache files automatically* — you won't silently load a BM25 index built with the wrong `b`/`k1`.

**Footgun:** `end_to_end_evaluation.py`'s `EndToEndEvaluator._initialize_search_indices()` (around line 1244-1262) hardcodes `force_reindex=False` for both indices — there is no config flag to force a rebuild from the main pipeline. To force a reindex, either delete the cache file directly or run `src/search.py`'s own `main()`, which does expose `FORCE_REINDEX_BM25`/`FORCE_REINDEX_SBERT`.

### 2. Keyword cache — one JSON file per dataset, keyed by query_id

- `cache/keywords/keybert_k10_div0.7_top10docs_mpnet_k1000_ngram1-2.json` (TREC-COVID, all 15 queries)
- `cache/keywords/doctor_reviews_keybert.json` (doctor-reviews, **only queries `1`-`6` of the 11**)

Generated by Stage 3 (`src/keyword_extraction.py` / `generate_doctor_review_keywords.py`) — see [PIPELINE.md](PIPELINE.md). Consumed by `sample_query_expansion()` in `src/end_to_end_evaluation.py`.

**Known, intentional behavior — not a bug:** `sample_query_expansion()` does `all_keywords.get(self.query_id, [])`. When a query_id has no cached entry (doctor-reviews queries `7`-`11`), this returns `[]`, which triggers:
```python
if not query_keywords:
    logger.warning(f"No keywords found for query {self.query_id}, using direct retrieval")
    return self.sample_direct_retrieval()
```
So for those 5 queries, the `query_expansion` method silently produces **the exact same sample as `direct_retrieval`** — same documents, same topics, same metrics. This is a real caveat for reading results (a "Query Expansion vs. Direct Retrieval" comparison is meaningless for those 5 queries specifically), not a pipeline defect. If you need real query-expansion behavior for queries 7-11, run `generate_doctor_review_keywords.py` with those queries added to its hardcoded `queries` list (repo root, ~line 65).

There's no force flag for this tier — regenerating means re-running the generation script, which currently always overwrites (`FORCE_REGENERATE_KEYWORDS = True` in `generate_doctor_review_keywords.py`).

### 3. IDF cache — per corpus size, used for the `topic_specificity` metric

- `cache/corpus_{len(corpus_dataset)}/idf_scores.pkl`

Computed once per corpus (keyed by document count) via `_compute_idf_scores()` / `_load_or_compute_idf()`. **Footgun:** the force flag is hardcoded `force=False` with the comment `# Never force - IDF computation is expensive` (`end_to_end_evaluation.py` `_load_or_compute_idf`) — if the corpus *content* changes without changing its *document count*, this cache goes stale silently. Delete the `.pkl` file manually to force a recompute.

### 4. Document samples — per query, per sampling method

- `results/{dataset}/{topic_model}/query_{id}/samples/{method}.pkl`

Controlled by `FORCE_REGENERATE_SAMPLES`. Uses `_load_or_compute_sample()`, which has a **cross-model sharing fallback**: since the same sampling methods produce identical documents regardless of which topic model consumes them, if a sample isn't cached under the current `topic_model_type`'s directory, it checks `bertopic` → `lda` → `topicgpt` (in that order) before computing from scratch. Note this fallback list does **not** include `hicode` — HiCode doesn't sample independently, it evaluates whatever documents the external HiCode run was given.

### 5. Topic models — per query, per sampling method, per topic model type

- `results/{dataset}/{topic_model}/query_{id}/topic_models/{method}_results.pkl` — always saved (the standardized result dict from `TopicModelWrapper`)
- `results/{dataset}/{topic_model}/query_{id}/topic_models/{method}_model.pkl` — only if `SAVE_TOPIC_MODELS = True` (BERTopic models are ~420MB each; 4 methods × 15 queries would be ~25GB, so this defaults off)

Controlled by `FORCE_REGENERATE_TOPICS`.

### 6. Evaluation results & aggregates — per query, per metrics-embedding-model

- `results/{dataset}/{topic_model}/query_{id}/results/{metrics_tag}/` — `per_method_summary.csv`, `pairwise_metrics.csv`, `topics_summary/`, `plots/`
- `results/{dataset}/{topic_model}/aggregate_results/{metrics_tag}/` — cross-query combined CSVs, statistical test outputs, aggregate plots

`{metrics_tag}` is `metrics_embedding_model_name.replace("/", "_").replace("-", "_")` (e.g. `all_mpnet_base_v2`, `BAAI_bge_base_en_v1.5`). This nesting exists **specifically so both embedding models' metric computations can coexist** without overwriting each other — see USAGE.md's Configuration Reference for why the metrics-embedding-model is a separate knob from the retrieval/BERTopic embedding model. Controlled by `FORCE_REGENERATE_EVALUATION`; aggregation itself has no force flag (it's cheap — it's just recombining already-computed per-query CSVs, so it always recomputes).

**HiCode uses this same tagged layout** (`results/{dataset}/hicode/query_{id}/results/{metrics_tag}/`), but gets there differently: since `evaluate_hicode.py` builds its `EndToEndEvaluator` via `object.__new__()` rather than the normal constructor, it has to manually compute `_metrics_tag` and build the tagged `results_dir` itself rather than inheriting it from `__init__`. If you add a new cache-path-relevant attribute to `EndToEndEvaluator.__init__`, remember it won't automatically reach the HiCode path — see PIPELINE.md's Stage 4b note.

## Cache logic (applies to every tier above)

```python
if cache_exists and not force_flag:
    load_from_cache()
else:
    compute()
    save_to_cache()
```

Nothing here detects that your *configuration* changed — only whether a force flag is `True` or the file is missing. Changing `BM25_B_PARAM` produces a new cache filename automatically (safe), but changing, say, MMR's λ or the KeyBERT diversity parameter does **not** change the samples cache filename (`{method}.pkl` has no parameter suffix) — you must set `FORCE_REGENERATE_SAMPLES = True` yourself after changing sampling-method internals, or you'll silently keep evaluating the old samples.

## Clearing cache

```bash
# Clear one query's results for one topic model (keeps samples, indices)
rm -rf results/{dataset}/{topic_model}/query_{id}/results/

# Clear one query's samples + topic models + results (full recompute for that query/model)
rm -rf results/{dataset}/{topic_model}/query_{id}/

# Clear search indices (forces BM25 + SBERT rebuild on next run)
rm -rf cache/indices/

# Clear IDF cache
rm -rf cache/corpus_*/
```
